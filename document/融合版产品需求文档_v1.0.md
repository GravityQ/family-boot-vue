## 1. 项目概述 (Project Overview)

### 1.1 产品定位
“家人在线”是一个**多端融合的在线族谱管理平台**。
- **前端 (用户侧)**：以**微信小程序**为核心载体，利用微信生态便于传播分享，降低老年用户和普通族人的使用门槛，侧重于“展示、查询、简易录入、社交分享”。
- **后端 (管理侧)**：提供 **Web 端后台**，侧重于“批量管理、复杂关系编辑、数据导出、系统配置”，供家族管理员和专业修谱人员使用。

### 1.2 核心价值
区别于传统单机版修谱软件，本项目强调：
1.  **协作性**：支持家族成员共同参与修谱，通过“提交-审核”机制保障数据准确性。
2.  **可视化**：通过高性能的树形图谱技术，直观展示庞大的家族关系。
3.  **严谨性**：基于严格的实体关系模型 (ER Model)，支持多配偶、继子女、过继等复杂中国式家庭关系。

## 2. 用户角色与权限 (Roles & Permissions)

采用 RBAC 模型，但在业务逻辑上对“家族创建者”进行特殊优待。

| 角色 | 定义 | 权限范围 | 审核规则 |
| :--- | :--- | :--- | :--- |
| **普通用户** (User) | 注册并登录的普通族人 | - 浏览已公开/已加入的族谱<br>- 搜索家族<br>- 提交新增/修改申请<br>- 收藏族谱 | **强审核**：所有增删改操作均需家族管理员审核通过后生效。 |
| **家族管理员** (Family Admin) | 家族创建者或被授权的核心成员 | - **管理家族**：修改简介、公告、设置隐私<br>- **成员管理**：直接增删改成员（无需审核）<br>- **审核权**：处理普通用户的提交申请<br>- **人员管理**：移除成员、指派其他管理员 | **免审核**：自身操作直接生效。<br>**被审核**：仅“删除家族”需系统管理员审核。 |
| **系统管理员** (System Admin) | 平台运营方 | - 审核家族创建申请<br>- 全局用户管理<br>- 敏感数据监管<br>- 系统配置 | 最高权限。 |

## 4. 数据模型设计 (Data Models)

基于复杂家庭关系（多配偶、离异、再婚）的稳健设计。

### 4.1 核心ER图概念
*   **Family**: 家族聚合根。
*   **Member**: 独立个体。
*   **FamilyUnit (家庭单元)**: 连接丈夫、妻子与子女的中间节点。解决“同父异母”、“同母异父”及“多婚”问题。

### 4.2 数据库Schema (DDL摘要)

```sql
-- 1. 家族表
CREATE TABLE `family` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '家族ID',
  `name` varchar(100) NOT NULL COMMENT '家族名称',
  `main_surname` varchar(50) NOT NULL COMMENT '主要姓氏',
  `location` varchar(200) DEFAULT NULL COMMENT '祖籍地址',
  `creator_id` bigint NOT NULL COMMENT '创建人ID',
  `status` tinyint NOT NULL DEFAULT '0' COMMENT '状态:0待审,1正常,2拒绝',
  PRIMARY KEY (`id`)
);

-- 2. 成员表
CREATE TABLE `member` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `family_id` bigint NOT NULL COMMENT '所属家族',
  `name` varchar(50) NOT NULL COMMENT '姓名',
  `gender` tinyint NOT NULL COMMENT '1男 0女',
  `birth_date` date DEFAULT NULL,
  `death_date` date DEFAULT NULL,
  `is_alive` tinyint DEFAULT '1',
  `intro` text COMMENT '行传/简介',
  `father_id` bigint DEFAULT NULL COMMENT '冗余字段加速查询',
  `mother_id` bigint DEFAULT NULL COMMENT '冗余字段加速查询',
  PRIMARY KEY (`id`)
);

-- 3. 家庭单元表 (核心关系表)
-- 一个家庭单元代表一段婚姻关系。子女挂载在家庭单元下，而非直接挂在父亲名下。
CREATE TABLE `family_unit` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `husband_id` bigint DEFAULT NULL,
  `wife_id` bigint DEFAULT NULL,
  `type` tinyint DEFAULT '1' COMMENT '1原配, 2续弦...',
  `status` tinyint DEFAULT '1' COMMENT '1婚姻中, 0离异',
  PRIMARY KEY (`id`)
);

-- 4. 成员-家庭关联 (子女表)
CREATE TABLE `member_parent_link` (
  `member_id` bigint NOT NULL COMMENT '子女ID',
  `family_unit_id` bigint NOT NULL COMMENT '所属家庭单元(由此确定父母)',
  PRIMARY KEY (`member_id`, `family_unit_id`)
);

-- 5. 审核日志表
CREATE TABLE `audit_log` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `entity_type` varchar(20) NOT NULL COMMENT 'MEMBER/FAMILY',
  `entity_id` bigint NOT NULL,
  `applicant_id` bigint NOT NULL COMMENT '申请人',
  `operation` varchar(20) NOT NULL COMMENT 'ADD/UPDATE/DEL',
  `content_snapshot` json COMMENT '修改内容快照',
  `audit_status` tinyint DEFAULT '0',
  PRIMARY KEY (`id`)
);
```

## 5. 接口设计 (API Overview)

遵循 RESTful 规范，URL 前缀 `/api/v1`。

### 家族相关
*   `POST /families` - 申请创建家族
*   `GET /families/search?kw=张` - 搜索家族
*   `GET /families/{id}/detail` - 家族详情
*   `PUT /families/{id}` - 修改家族信息 (Admin only)

### 成员与图谱
*   `GET /families/{id}/tree` - **获取全量/局部树数据** (关键接口，需优化性能)
    *   *Response*: 嵌套的 JSON 结构，包含 `nodes` (成员) 和 `links` (关系)。
*   `POST /members` - 添加成员 (触发审核或直接添加)
*   `GET /members/{id}` - 获取成员详情

### 审核相关
*   `GET /audits/pending` - 获取待审核列表
*   `POST /audits/{id}/approve` - 通过
*   `POST /audits/{id}/reject` - 驳回

## 6. 非功能需求 (Non-functional)

### 6.1 性能要求
*   **图谱加载**：Web端支持 2000+ 节点流畅渲染；小程序端支持 500+ 节点流畅渲染（超出部分采用懒加载/点击展开策略）。
*   **并发**：支持 100+ TPS（针对查询接口）。

### 6.2 安全隐私
*   **数据脱敏**：API 在返回普通用户查询结果时，自动隐藏在世成员的手机号、身份证等敏感字段。
*   **越权防护**：严格校验 `family_id`，防止用户通过修改 URL ID 访问其他家族未公开数据。

## 7. 迭代计划 (Roadmap)

### Phase 1 (MVP)
*   基础 RBAC 权限。
*   家族增删改查 + 审核。
*   成员树形展示 + 基础增删改。
*   小程序端核心流程跑通。

### Phase 2 (体验优化)
*   老照片上传与图集展示。
*   导出高清 PDF 族谱。
*   “纠错”审核流完善。

### Phase 3 (高级功能 - 规划中)
*   **OCR 识别**：拍照识别纸质族谱，自动录入。
*   **寻根匹配**：基于大数据推荐可能的亲戚关系。
*   **社区功能**：家族公告、纪念日提醒。
