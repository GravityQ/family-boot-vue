# 芋道 (yu2dao) Constitution

## 核心原则

### 一、模块化设计原则

- **单一职责**：每个模块只负责一个明确的业务领域或技术职责
- **高内聚低耦合**：模块内部功能紧密相关，模块间依赖最小化
- **独立演进**：模块可独立开发、测试、部署和维护
- **清晰边界**：模块间通过明确定义的接口通信，避免循环依赖

**原则说明**：模块化设计是系统可维护性的基础。通过将系统拆分为职责明确的模块，可以提高开发效率、降低维护成本，并支持团队并行开发。所有新功能必须首先确定其所属模块，并评估对现有模块边界的影响。

### 二、COLA架构 (Clean Object-oriented & Layered Architecture)

- **分层清晰**：严格遵循适配层、应用层、领域层、基础设施层的分层结构
- **依赖倒置**：高层模块不应依赖低层模块，二者都应依赖抽象
- **南向网关**：领域层通过依赖倒置访问基础设施层
- **CQRS分离**：查询和命令职责明确分离，避免混合使用

**原则说明**：COLA架构提供了清晰的架构引导，帮助团队在大型应用中保持代码结构的整洁。适配层处理外部请求，应用层协调业务流程，领域层包含核心业务逻辑，基础设施层提供技术能力实现。

### 三、阿里巴巴开发规范 (Alibaba Java Development Manual)

- **强制遵守**：所有Java代码必须严格遵守阿里巴巴Java开发手册【强制】规则
- **规约优先**：在代码风格、命名规范、异常处理等方面统一标准
- **静态检查**：集成PMD、Checkstyle等工具进行自动化代码规范检查
- **Code Review**：代码审查时必须检查规范遵守情况

**原则说明**：统一的编码规范是团队协作的基础。阿里巴巴Java开发手册是业界广泛使用的中文规范标准，它能确保不同开发者编写的代码风格一致，提高代码可读性和可维护性。

### 四、最小依赖原则 (Minimal Dependency Principle)

- **按需引入**：只引入真正需要的依赖，避免"以防万一"式依赖
- **版本锁定**：所有依赖版本必须在根pom.xml统一管理
- **依赖审查**：新增或升级依赖必须经过技术评审
- **替代优先**：能用标准库解决的问题，不引入第三方库

**原则说明**：每个依赖都是潜在的维护负担和安全风险。通过严格控制依赖，可以减少包体积、降低冲突概率、简化升级路径。新增依赖前必须评估其必要性、活跃度和社区支持情况。

### 五、代码规范和样式统一

- **统一格式化**：使用统一的IDE代码格式化配置
- **自动化检查**：Git提交前自动执行代码格式检查
- **命名一致**：包名、类名、方法名、变量名遵循统一规则
- **文档完整**：所有公共API必须有JavaDoc注释

**原则说明**：代码不仅是给机器执行的，更是给人阅读的。统一的代码风格和样式可以减少代码审查的噪音，让开发者专注于业务逻辑而非格式问题。所有开发者必须共享相同的格式化配置。

### 六、中文优先原则 (Chinese First Principle)

- **中文文档**：speckit相关文档、需求规格说明、任务描述等优先使用中文
- **双语支持**：必要时提供中英文对照，但中文版本为主导版本
- **注释中文**：代码注释尽可能使用中文，便于母语开发者理解
- **本土化**：所有面向开发者的工具、模板、提示信息优先使用中文

**原则说明**：speckit工具链是为本土化团队设计的，使用中文可以提高沟通效率，降低理解门槛。但这不影响代码层面向的英语标准（如类名、方法名仍遵循Java规范）。

### 七、测试驱动开发 (TDD - Test Driven Development)

- **先测试后实现**：所有功能开发必须先写测试用例
- **测试覆盖**：核心业务逻辑测试覆盖率要求≥80%
- **集成测试**：模块间集成点必须有集成测试覆盖
- **持续验证**：CI/CD流水线必须执行全部测试用例

**原则说明**：测试是保证代码质量的关键手段。TDD不仅能确保代码的可测试性，还能帮助开发者更好地理解需求。测试用例就是活的文档，它描述了代码的预期行为。

### 八、渐进式演进 (Incremental Evolution)

- **小步快跑**：每次改动范围尽可能小，确保可独立编译和运行
- **保持绿色**：每次提交后代码必须能通过编译和测试
- **可回退**：避免一次性重写整个函数或模块，基于现有逻辑逐步调整
- **局部优先**：优先修复错误、提取小函数、增加注释、微调逻辑

**原则说明**：软件开发是渐进式过程，大规模重构风险高。通过小步快跑，每次只解决一个问题，可以降低风险，保持代码库始终处于可部署状态。

## 质量门禁

### 代码质量要求

- **静态分析**：SonarQube质量门禁必须通过，不允许新增Major及以上级别问题
- **测试覆盖**：新增代码必须达到80%的测试覆盖率
- **Code Review**：所有代码必须经过至少一名其他开发者审查
- **构建通过**：PR合并前必须确保CI/CD流水线全部通过

### 安全合规要求

- **OWASP Top 10**：必须防范OWASP Top 10安全风险
- **敏感信息**：禁止在代码中硬编码密码、密钥等敏感信息
- **注入防范**：所有外部输入必须进行严格校验和转义
- **日志脱敏**：日志输出不得包含敏感个人信息

## 治理与修订

### 修订流程

本项目宪法是最高治理文件，所有开发实践必须遵守。任何对宪法的修订必须经过：

1. **提案阶段**：明确修订理由和预期效果
2. **评审阶段**：至少2名核心维护者评审通过
3. **试行阶段**：在小范围内试行验证效果
4. **正式生效**：完成文档更新和团队培训

### 合规检查

- 所有PR审查必须验证是否符合宪法原则
- 复杂度增加必须提供充分理由和文档说明
- 技术选型偏离原则时必须记录例外情况和补偿措施

### 版本管理

宪法版本采用语义化版本控制：

- **MAJOR**：原则性条款的移除或重新定义
- **MINOR**：新增原则章节或扩大指导范围
- **PATCH**：条款澄清、措辞优化、错别字修正
