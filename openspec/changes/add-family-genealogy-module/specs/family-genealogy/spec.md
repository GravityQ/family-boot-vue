## ADDED Requirements

### Requirement: 家族创建与管理
系统 MUST 支持已登录用户创建和管理家族实体，并提供基本元数据与隐私控制能力。

#### Scenario: 创建家族申请
- **WHEN** 已登录用户提交创建家族申请（包含必填字段：家族名称、主要姓氏，可选字段：祖籍、简介、封面图）
- **THEN** 系统必须校验该家族名称在平台范围内唯一
- **AND** 创建一条状态为“待审”的家族记录
- **AND** 通知系统管理员有新的家族创建申请待审核

#### Scenario: 审核通过家族创建
- **WHEN** 系统管理员在管理端审核通过一条待审的家族创建记录
- **THEN** 该家族状态必须从“待审”变更为“正常”
- **AND** 该申请人必须成为该家族的家族管理员

#### Scenario: 带隐私控制的家族搜索
- **WHEN** 任意用户（包括未登录用户）按照家族名称和/或姓氏搜索家族
- **THEN** 系统必须返回符合条件的家族分页列表
- **AND** 对于隐私等级较高的家族，在用户尚未加入或被邀请前，只能返回脱敏的家族概况字段（如：名称、成员数、地区、封面等），不得暴露详细族谱。

### Requirement: 成员树谱可视化 API
系统 MUST 提供面向前端的树形数据接口，用于渲染包含多配偶与父子关系在内的家族树谱。

#### Scenario: 小规模家族的全量树加载
- **WHEN** 某家族成员请求查看其所属家族的树谱
- **AND** 该家族成员总量低于配置阈值（例如 1000 人）
- **THEN** 系统必须一次性加载该家族全部 `member` 记录及关联的 `family_unit` 记录
- **AND** 在内存中组装成树结构友好的返回格式（包含 rootId、成员列表、配偶与子女关系等）
- **AND** 在小规模家族的性能预算范围内完成响应。

#### Scenario: 非成员访问树谱的受限行为
- **WHEN** 非家族成员尝试访问某家族的完整成员树谱
- **THEN** 系统必须根据该家族的隐私设置拒绝访问，或仅返回高层级、非敏感的概要信息
- **AND** 不得暴露详细亲属关系或敏感个人信息。

### Requirement: 成员详情与亲属关系
系统 MUST 提供成员详情接口，返回关键生平信息及可导航的直系亲属关系。

#### Scenario: 获取成员详情
- **WHEN** 有访问权限的用户请求某个成员（其有权访问的家族内）的详情
- **THEN** 系统必须返回该成员的核心信息（姓名、性别、辈分、生卒日期、头像、人物行传等）
- **AND** 必须包含结构化的父母、配偶、子女等关系信息，以支持前端进行上下游导航。

### Requirement: 用户提交变更与审核流程
系统 MUST 支持普通用户提交对家族和成员数据的变更请求，并通过审核工作流在生效前进行审批。

#### Scenario: 申请新增成员
- **WHEN** 普通家族成员在前端发起新增成员（例如子女或配偶）的申请
- **THEN** 系统必须创建一条 `audit_log` 记录，操作类型为 CREATE，`new_json` 中包含拟新增成员的数据
- **AND** 在审核通过前，不能将该成员写入正式的 `member` 表。

#### Scenario: 申请修改成员
- **WHEN** 普通家族成员发起对已有成员信息的纠错或修改申请
- **THEN** 系统必须创建一条 `audit_log` 记录，操作类型为 UPDATE，`old_json` 保存当前数据快照，`new_json` 仅包含变更字段
- **AND** 在家族管理员审核通过之前，正式 `member` 记录必须保持不变。

#### Scenario: 家族管理员审核通过
- **WHEN** 家族管理员在审核工作台中查看并通过一条所属家族的待审记录
- **THEN** 系统必须将对应变更应用到正式实体（如 `member` 或 `family`）
- **AND** 将该 `audit_log` 记录标记为已通过状态，并记录审核人及审核时间。

#### Scenario: 家族管理员审核驳回
- **WHEN** 家族管理员在审核工作台中驳回一条待审记录并填写驳回原因
- **THEN** 系统必须将该 `audit_log` 记录标记为已驳回状态，并保存驳回原因
- **AND** 通知原申请人该申请已被驳回及原因说明。

### Requirement: 管理端成员管理
系统 MUST 允许家族管理员通过管理端接口直接管理成员数据，但需要安全约束与保护。

#### Scenario: 家族管理员直接新增成员
- **WHEN** 家族管理员调用管理端成员新增接口并传入合法的成员数据
- **THEN** 系统必须直接在 `member` 表中插入记录，而无需创建中间 `audit_log` 记录
- **AND** 新增成员应出现在后续树谱与成员详情查询结果中。

#### Scenario: 安全删除成员
- **WHEN** 家族管理员尝试删除一名仍存在子女记录的成员
- **THEN** 系统必须默认阻止直接不可逆删除
- **AND** 要求管理员显式选择后续处理方式（如级联删除或将子女转移到其他父母）后，才能继续执行。

### Requirement: 家族族谱的非功能行为
系统 MUST 满足家族族谱相关的性能、易用性和数据安全等非功能约束。

#### Scenario: 小规模家族树的加载性能
- **WHEN** 小程序或移动端客户端请求一个成员数约在 500 人级别的家族树谱
- **THEN** 后端必须在正常网络条件下，以足够快的速度返回树谱数据，使前端能够在约 2 秒内完成首屏渲染。

#### Scenario: 面向长辈用户的易用性
- **WHEN** 前端以“长辈模式 / 大字模式”渲染成员详情和树谱页面
- **THEN** 后端 API 必须提供足够清晰且简明的字段（如关键标签、简洁文案），以便前端在不修改后端的情况下，通过放大字号和调整布局提升可读性。

#### Scenario: 敏感信息保护
- **WHEN** 客户端请求的数据涉及在世成员的敏感字段（例如手机号、身份证号、详细住址等）
- **THEN** 系统必须对这些敏感数据进行加密存储
- **AND** 默认仅返回脱敏后的信息（或完全隐藏），除非有更严格的安全策略要求禁止前端展示。
