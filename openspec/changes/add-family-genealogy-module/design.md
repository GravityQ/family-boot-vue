## 背景与上下文（Context）
- 产品：**「家人在线」Family Online**，用于协同维护家族成员信息，支持可视化树谱与审核流程。
- 技术基线：基于芋道后端（Spring Boot 3 + MyBatis Plus + Redis）以及多模块 Maven 结构（`yudao-module-*`）。
- 本次范围：在后端新增 `yudao-module-family` 模块，用于建模家族（family）、成员（member）、家庭单元（family_unit，婚姻关系）及审核记录（audit_log），并提供 App 端与管理端的 API。

核心领域实体（参考 TDD）：
- `family`：家族元信息、隐私设置、创建人、状态、租户关联等。
- `member`：自然人基础信息，包含辈分、出生/去世日期、父母关系、排序等。
- `family_unit`：家庭（婚姻）单元，用来表达多配偶、离异、再婚等复杂关系。
- `audit_log`：普通用户发起的创建/修改/删除操作，在管理员审核前的中间态存储。

## 目标与非目标（Goals / Non-Goals）
- 目标（Goals）：
  - 提供一套清晰的后端家族族谱能力，与 PRD、API 文档、数据库设计保持一致。
  - 在同一数据模型之上，同时支持 App 端（小程序）和管理端的接口调用。
  - 明确普通用户 / 家族管理员 / 系统管理员在审核、编辑等行为上的差异化逻辑。
  - 在约 1000 人量级的家族规模下，树谱构建算法可用且性能可接受，并为更大规模保留扩展空间。
- 非目标（Non-Goals）：
  - 不在本提案中实现具体前端 UI，仅约束 API 与后端行为。
  - 不重构或替换既有的 RBAC、多租户、用户体系，只在其之上集成家族角色与访问控制。
  - 不一次性实现所有高级功能（如跨家族跳转、极大规模族谱分页展示等），这些可以拆分为后续迭代。

## 关键技术决策（Decisions）
- 决策：**模块边界**
  - 新增独立 Maven 模块 `yudao-module-family`，下沉家族相关领域模型与业务逻辑，避免污染系统/基础设施模块。
- 决策：**数据模型**
  - 采用 TDD 中给出的 `family`、`member`、`family_unit`、`audit_log` 作为初始 MySQL 规范结构。
- 决策：**API 分层**
  - App/小程序相关接口统一以 `/app-api/family/v1` 为前缀，管理端接口统一以 `/admin-api/family` 为前缀，遵循现有芋道 API 组织方式。
- 决策：**树谱构建策略**
  - 对成员数 < 1000 的家族，一次性加载该家族的全部 `member` 和相关 `family_unit` 记录，在内存中组装树形结构返回。
  - 对于更大规模家族，仅在本提案中预留“按层级加载”或“以某人为中心 N 代视图”等扩展点，不强行一次性设计完。
- 决策：**审核语义**
  - 普通用户发起的成员/家族变更统一落入 `audit_log`，审核通过前不影响正式表；
  - 家族管理员在管理端可以直接操作正式表（新增/部分修改），同时也负责审核普通用户的变更请求。

## 风险与权衡（Risks / Trade-offs）
- 风险：**大体量家族的性能问题**
  - 对于 > 1000 成员的家族，全量加载与内存树构建可能会在延迟与内存消耗上出现瓶颈。
  - 权衡与缓解：先实现简单可用的全量方案并设定合理阈值，后续通过按层级加载、局部视图等方式优化。
- 风险：**复杂关系建模带来的接口复杂度**
  - 多配偶、离异/再婚、过继/抱养等关系会让接口返回结构和前端渲染逻辑变得复杂。
  - 权衡与缓解：通过 `family_unit` 在数据模型中统一处理复杂关系，对外暴露稳定的 DTO 结构，由前端自由选择呈现方式。
- 风险：**权限与隐私控制不当导致的数据泄露**
  - 如果家族成员身份、角色、隐私等级判断不严谨，可能向无权限用户泄露敏感个人信息。
  - 权衡与缓解：在 Service 层集中封装访问校验逻辑，树谱与详情 API 一律先做家族成员与隐私级别检查，再返回数据。

## 迁移与发布计划（Migration Plan）
- 初次引入：
  - 通过新增数据库表完成 schema 扩展，不对现有模块做破坏性修改。
  - 在 `yudao-server` 中以新增模块方式集成 `yudao-module-family`。
- 灰度与推广：
  - 初期可仅向内部管理员与少量测试用户开放，用于录入和验证示例家族数据。
  - 稳定后再向正式用户开放 App 端接口。
- 回滚策略：
  - 若发布出现严重问题，可在不影响其他模块的前提下，从 `yudao-server` 中临时移除 `yudao-module-family`，数据库表保持空置状态以便后续继续使用。

## 待确认问题（Open Questions）
- 家族成员与现有用户/租户之间的绑定粒度：例如，一个用户是否可以跨多个租户加入多个家族，还是与某个租户/组织结构强绑定？
- PRD 中提到的跨家族关联（如配偶在另一家族）的具体上线节奏：是纳入 v1 范围，还是拆分为后续能力？
- 对于在世成员的敏感信息，除了加密与脱敏外，是否有更严格的合规要求（如不同地区的隐私法规差异）需要在规范中写明？
